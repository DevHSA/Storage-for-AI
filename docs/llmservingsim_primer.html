LLM Serving from the Ground Up

A plain-English primer for LLMServingSim: how an LLM is built, how it runs (prefill & decode), how big the KV cache is, and how every concept maps to our code — with worked numbers for Llama-3.1-8B and its 4-layer copy.

Who this is for
You've heard "tokens", "KV cache", "prefill/decode", "TP", "batch size" — but the details are fuzzy. This primer builds each idea from scratch, gives the exact formula, then points at the line of our code that implements it, with concrete numbers. It's the companion to the main guide (which covers the simulator's layers and the JBOF memory-tier study) — read this first if the vocabulary is new.

1. What is an LLM (and what are all those numbers)?

A large language model is a stack of identical transformer layers. Text is cut into tokens (word pieces); each token becomes a vector; the stack transforms those vectors; the last layer predicts the next token. Generation repeats one token at a time.

Every dimension you'll see is just a size in that picture:

TermWhat it isLlama-3.1-8Bmini4L
num_hidden_layershow many transformer layers are stacked (the depth)324
hidden_sizewidth of the vector carried between layers (per token)40964096
num_attention_headsparallel "attention" views per layer (Q heads)3232
num_key_value_headsK/V heads — fewer than Q heads (this is GQA)88
head_dimwidth of one head = hidden_size ÷ heads128128
intermediate_sizethe MLP's inner width (expand then shrink)1433614336
vocab_sizenumber of possible tokens (embedding + lm_head width)128256128256
weight (fp16)total parameters × 2 bytes (see §2)~14.96 GiB~3.58 GiB
GQA — why there are only 8 KV heads, not 32
Plain attention would keep a Key and Value for all 32 heads. Grouped-Query Attention shares each K/V head across a group of Q heads — here 32 Q heads share 8 K/V heads (ratio 4). It cuts the KV cache to ¼ with almost no quality loss. This is why the KV size below uses num_key_value_heads (8), not num_attention_heads (32).

2. The two things that live in GPU memory

A GPU serving an LLM holds two big things:

  1. Weights — the model's learned parameters. Fixed size, loaded once. For 8B in fp16 that's ~15 GB; for mini4L, ~3.6 GB.
  2. KV cache — the per-conversation "memory" of tokens seen so far. Grows with every token and every concurrent request. This is the star of §4.
NPU KV capacity = npu_mem − model_weight

So a bigger model leaves less room for KV. For the full 8B on a small NPU there's very little KV headroom, which is exactly why our study uses the 4-layer mini4L (smaller weight → more KV room).

In our code
# serving/core/memory_model.py
self.weight     = self.get_weight()          # ~14.96 GiB for 8B (line ~57, 136-164)
self.mem_for_kv = self.npu_mem - self.weight # KV region (line 65)
get_weight() sums embedding + layers + lm_head (÷ TP); see §6.

3. How inference runs: prefill vs decode

Serving one request has two phases, with very different behavior:

PrefillDecode
Processesthe whole prompt, in parallelone new token per step
Bottleneckcompute (lots of math)memory bandwidth (reads all KV)
Metric it drivesTTFT (time to first token)TBT / TPOT (time per output token)

This split is why our memory-tier study focuses on TTFT: reusing a cached prompt prefix (or reloading it from a fast tier) shortens prefill → lower TTFT, while decode (TBT) is unaffected. TTFT = arrival → first token; TPOT = (total − TTFT) ÷ (output−1); ITL = the per-step decode latencies.

In our code
A request is in prefill while it still has prompt tokens left to compute:

4. The KV cache and exactly how big it is

During attention, each token produces a Key and a Value vector at every layer. To avoid recomputing them for every future token, they're cached. That cache is the KV cache, and it grows by a fixed amount per token.

bytes per token = 2 × (num_kv_heads × head_dim) × num_layers × bytes_per_element

Reading it left to right: 2 = one Key + one Value; num_kv_heads × head_dim = the size of one token's K (and of its V) — call it kv_dim; num_layers = every layer keeps its own KV; bytes_per_element = 2 for fp16/bf16 (or 1 for fp8).

Worked numbers
Llama-3.1-8B: kv_dim = 8 × 128 = 1024, layers = 32, fp16 → 2 × 1024 × 32 × 2 = 131,072 B/token (128 KB). A 2,048-token prompt = 268 MB of KV; a 4,096-token one ≈ 537 MB — for a single request.
mini4L (4 layers): 2 × 1024 × 4 × 2 = 16,384 B/token (8× smaller — that's the whole reason it's cheap to simulate).
KV capacity (tokens) = (npu_mem − weight) ÷ bytes_per_token

Example: an NPU with ~8 GB free after weights, at 131 KB/token, holds ≈ 61,000 tokens of KV. Serve 100 concurrent 2,000-token conversations and you need 100 × 2000 × 131 KB ≈ 26 GB — more than one GPU has, which is precisely why KV must spill to slower tiers (the main guide's story).

Paging: the KV cache is allocated in blocks

Rather than grow byte-by-byte, KV is allocated in fixed blocks of --block-size tokens (default 16), like OS memory pages (this is vLLM's PagedAttention). A 17-token sequence uses 2 blocks. Paging avoids fragmentation and lets two requests that share a prefix share the same blocks — the foundation of prefix caching (§8).

In our code
# serving/core/memory_model.py:186 — the exact formula above, per GPU
def get_kv(self, seq):
    return 2 * self.kv_dim * seq * self.n_layer * self.kv_fp // self.num_npus
# kv_dim = num_kv_heads·head_dim ; kv_fp = bytes/elem (2=fp16, 1=fp8) ; //num_npus = TP split (§6)

5. Sequences, batches, and continuous batching

To serve many users at once, the engine processes several requests together each step.

  • Sequence — one request's token stream (its prompt, then its generated tokens).
  • Batch — the set of sequences advanced together in one step. It can mix prefill requests (still reading their prompt) and decode requests (emitting one token).
  • max_num_seqs — the max number of concurrent sequences (the batch width). It caps in-flight KV so the NPU isn't over-committed.
  • max_num_batched_tokens — the max tokens processed in one step (the token budget). Decode uses 1 token/request; a prefill can use many.
  • Continuous batching (vLLM-style) — requests join and leave the batch every step, instead of waiting for a whole batch to finish. This is what keeps GPUs busy under real traffic.
Connecting to the metrics
Because prefill and decode are mixed in a batch, max_num_batched_tokens and max_num_seqs together decide how much prefill vs decode happens per step — which is why they matter for TTFT (prefill throughput) and TBT (decode cadence). Our examples use --max-num-seqs 8.
In our code
Each simulation step, schedule_base() runs five steps — (1) hand out the token budget (chunked prefill), (2) size the KV needed, (3) evict if it won't fit, (4) allocate, (5) assemble the Batch (its q_list, prefill/decode counts). 6. Scaling across GPUs (TP / PP / EP / DP)

One GPU isn't enough for big models or high load, so the model/work is split across GPUs:

KindWhat it splitsEffect on per-GPU weightEffect on per-GPU KV
TP tensor-paralleleach layer's matrices and the KV heads, within one forward pass÷ TP÷ TP
PP pipelinethe layers across GPUs (GPU 0 does layers 0–k, etc.)÷ PP (fewer layers each)÷ PP (fewer layers each)
EP expert-parallelthe experts of an MoE model÷ EP (experts)unchanged
DP data-parallelnothing — full model replicated, each copy takes different requestsunchangedunchanged (own cache)

The one that changes KV size is TP: with TP=2, the 8 KV heads are split 4-and-4, so each GPU holds half the KV per token. That's the // num_npus in get_kv.

Why our numbers use the full KV per token
Every JBOF example runs TP = 1 (one GPU per model instance), so there's no KV division: per-GPU KV/token = the full 131,072 B (8B) or 16,384 B (mini4L). If we used TP=2 those would halve. (Racks/pods scale by adding independent instances, not by raising TP.)
In our code
# get_kv divides by num_npus (= TP degree for one instance):
2 * kv_dim * seq * n_layer * kv_fp // num_npus        # memory_model.py:186
# get_weight shrinks each block by TP and uses fewer blocks under PP:
weight = emb + _get_weight_per_block(tp,ep,fp) * (n_layer // pp) + lm_head   # :136-184
config_builder.py resolves tp_size/pp_size/ep_size; num_npus = tp_size × pp_size. Worked check: 8B weight at TP=1 ≈ 14.96 GiB; at TP=2 ≈ 7.48 GiB (halved) — confirming TP splits weight.

7. How the simulator represents "model + hardware"

Everything above is sizes. To get timings, the simulator combines two inputs:

  1. The model architecture — the configs/model/<name>.json above (via get_config). Drives weight and KV sizes.
  2. Measured performance tables — the profiler database under profiler/perf/<hardware>/<model>/<dtype>/tp<N>/ (dense.csv, attention.csv, per_sequence.csv). These are real per-operation latencies (in ns) captured by a vLLM-based profiler on actual hardware, keyed by hardware + model + dtype + TP.

The trace generator loads both, then replays num_hidden_layers layers, looking up each operation's latency from the tables, to synthesize the per-batch trace that ASTRA-Sim times. This is the "model + hardware → per-operation latency" link — and it's why the 4-layer mini4L reuses the 8B per-layer timings, just 4× instead of 32×.

This is the bridge to the main guide
Sizes (this primer) + measured per-op latencies (the profiler) → a trace → ASTRA-Sim turns it into cycles. That "two brains" pipeline (Python decides what, ASTRA-Sim computes how long) is the subject of the main guide.

8. Prefix caching & the memory tiers (the bridge)

Now the pieces connect. Many requests share a prompt prefix (a system prompt, a document). Since that prefix's KV is identical, we can reuse it instead of recomputing prefill — a direct TTFT win (§3). The KV is stored in a tree keyed by token blocks (§4's paging), so a shared prefix shares blocks.

But the KV cache overflows the GPU (§4's capacity math), so reused prefixes are kept in a hierarchy of memory tiers — NPU → CPU → FLASH → JBOF → COLDSTORE — and a reuse is served from the shallowest tier that still holds it. When a fast pooled tier (JBOF) holds it instead of slow network storage, TTFT stays low even at pod scale.
