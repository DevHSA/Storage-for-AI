Introducing LLMServingSim

A hands-on tour of our tiered-memory LLM-serving simulator. We start by running a small example and reading its output, then peel back the layers, then scale up toward a real Vera Rubin pod — easing into the memory-tier work we added.

1. Overview — the two brains

New to LLM serving?
If terms like tokens, KV cache, prefill/decode, TP, batch size are fuzzy, read the companion "LLM Serving from the Ground Up" primer first — it builds every concept from scratch (with worked numbers) and ties it to this codebase; then this guide reads easily.

LLMServingSim answers "what if?" questions about serving giant models on hardware we may not have on the bench — new memory tiers, bigger racks, different caching — and returns throughput and latency without the real cluster.

It has two brains. The Python layer (a vLLM-style serving frontend) decides WHAT happens — which requests batch together, where each request's KV cache lives, what to reuse. ASTRA-Sim (a C++ analytical backend) computes HOW LONG it takes — compute, network, and memory-access time. They talk through a simple per-batch text trace.

2. Your first runs — from 1 GPU to 8

We ease in on a single GPU to watch the tiers work, then do a full 8-GPU run and read every part of its output.

The gentlest start — one GPU

The simplest possible run: 1 GPU, the mini model, 120 distinct contexts that are then reused. As each context is computed it fills the NPU, spills to CPU, and lands in the deep tier; when it is reused, it is served straight back from wherever it survived:

Tier       Hit tokens    Hit %  Reload(ms)   Usage(MB)   Cap(GB)   % used
NPU                 0    0.00%        0.00      320.00      0.32  98.301%
CPU                 0    0.00%        0.00      608.00      0.85  69.853%
JBOF           245760   49.90%      104.41     3866.25     18.80  20.083%
COLDSTORE           0    0.00%        0.00     3866.25    188.00   2.008%
1 GPU, WITH JBOF — the NPU is full, so the reused KV comes back from JBOF

With JBOF that reused KV returns in 104 ms → 73.6 req/s. Run the same workload on a config with no JBOF tier and the reuse falls to COLDSTORE: 1,289 ms → 54.0 req/s. The reload is ~12× slower; at this tiny scale that is only ~1.4× throughput — but that advantage grows sharply as we scale out (the chart in §1, and §7). Everything below is this same mechanism, measured properly.

Now scale to 8 GPUs

The smallest example that exercises everything across instances: 8 GPUs, the same model, and a workload that reuses prefixes so the tiers get used — the run we'll read in detail.

Two more you'll see: --enable-chunked-prefill (on by default — splits a long prompt across steps) and --max-num-batched-tokens (the per-step token budget).

Every tier block carries the same knobs — this is the heart of the tier feature:

KnobUnitMeaning
mem_sizeGiBCapacity of the tier.
mem_bwGB/sThe media's bandwidth (HBM 22 000, LPDDR 1 000, flash 64, disk 4).
mem_latencynsThe media's access latency (HBM ~10, LPDDR ~120, flash ~80 000, disk ~2 000 000).
link_bw / link_latencyGB/s / nsThe network hop to reach a pooled tier — present only for JBOF & COLDSTORE (they sit behind a BlueField/RDMA fabric).

Scope: NPU is per-GPU; CPU and FLASH are per-rack; JBOF and COLDSTORE are one pool shared across the whole pod. (These specific numbers are a proportionally-scaled Vera Rubin — see §5.)

CPU scope — --cpu-scope per_node (default) vs per_instance
By default the CPU tier is one pool per rack, shared by all its GPUs, so a prefix computed on one GPU can be reused from CPU by another. Real hardware often attaches host memory per GPU (Vera Rubin pairs 1 Vera CPU with 2 Rubin GPUs over private NVLink-C2C LPDDR). Passing --cpu-scope per_instance gives each GPU its own private CPU pool (sized at the rack's cpu_mem, so total CPU scales with GPUs-per-rack). The consequence is faithful: cross-GPU prefix reuse can no longer be served from CPU and instead routes to the pod-wide JBOF/COLDSTORE pool — exactly how a real pod shares KV across GPUs (via pooled CMX/flash, not host DRAM). Same-GPU reuse still hits CPU. On the 2-GPU example this splits a 39-token reuse into 20 (same-GPU→CPU) + 19 (cross-GPU→JBOF); with per_node all 39 come from CPU.

2cThe input workload file

The dataset is one JSON object per request:

{"input_toks": 2048, "output_toks": 4, "arrival_time_ns": 0,
 "input_tok_ids": [1, 2, 3, ... 2048], "output_tok_ids": [500000000, ...]}
one line of workloads/pod_prop_8gpu.jsonl
FieldMeaning
input_toks / output_toksPrompt length and number of tokens to generate.
arrival_time_nsWhen the request arrives (simulation clock). 0 = part of the opening burst.
input_tok_ids / output_tok_idsThe actual token ids. These decide prefix reuse: two requests that share a leading id sequence share cached KV.

Our generator (make_rack_fill.py) builds the workload in two phases, which is exactly how we force the tiers to fill and then get reused:

  • Phase 1 — fill: N distinct long contexts (unique token ids). Computing them fills NPU, then spills to CPU, then to the deep pool — every context's KV lands somewhere.
  • Phase 2 — reuse: re-send each context (oldest first) plus a short new tail. By now the old context has been evicted from NPU/CPU but survives in the deep tier, so each reuse reloads it from JBOF (or, without JBOF, from the far slower COLDSTORE).

Prefill-heavy by design. Each request is a long 2048-token prompt with only a 4-token output, so the work is dominated by prefill, not decode. That is deliberate: prefix caching's payoff is on the prefill path (reusing a prompt's KV skips recompute, and a deep-tier reload happens before the first token). Tiny outputs keep decode minimal, so the tier effect shows up cleanly in TTFT while TBT (decode) stays flat.

Deep dive: the generator script & its arguments
python workloads/generators/make_rack_fill.py <out.jsonl> <n_ctx> <ctx_len> <tail_len> <out_len> <gap_ms>
# the 8-GPU example:
python workloads/generators/make_rack_fill.py workloads/pod_prop_8gpu.jsonl 450 2048 8 4 3000
ArgExampleWhat it does
out.jsonlpod_prop_8gpu.jsonlOutput path for the generated trace.
n_ctx450Number of distinct contexts — chosen so the working set overflows NPU+CPU into the deep tier (larger for more GPUs).
ctx_len2048Prompt length per context. Long → prefill-heavy; this is also the KV reloaded on reuse.
tail_len8New tokens appended on reuse, so it is a genuine "shared prefix + a little new" request.
out_len4Tokens generated per request. Small → decode is minimal, isolating the prefill/tier effect.
gap_ms3000Delay before phase 2, so phase-1 fill completes (and shallow tiers evict) before reuse starts.

Phase 1 writes n_ctx distinct prompts at arrival=0 (a saturating burst); Phase 2 re-sends each (oldest first) as context + tail at arrival=gap_ms. Disjoint token-id ranges per context guarantee genuinely distinct KV, so a reuse is a true cache hit and a miss is a true recompute/reload.

2dReading the output

The run prints three blocks. First, throughput:

Total latency (s):                    3.401

How throughput is computed
Total latency (s) = Total clocks (ns) / 1e9 — the final simulation-clock time (the sim runs at 1 GHz, so 1 clock = 1 ns). Then:
  • Request throughput = requests ÷ Total latency
  • Total token throughput (tok/s) = (Total input tokens + Total generated tokens) ÷ Total latency
Input tokens count the full prompt, including reused prefix-hit tokens (this is effective prompt throughput, matching vLLM). Worked example for this 8-GPU run: (1,846,800 + 3,600) ÷ 3.401 s ≈ 544,144 tok/s. Since a JBOF vs no-JBOF pair runs the identical workload (same token counts), the tok/s ratio equals the latency (and req/s) ratio.

3. Under the hood — the three layers

That run flowed through three layers. Now that you've seen the output, here's what produced it.

Layer 1 — the Python frontend (serving/)

A vLLM-style control plane. Each loop iteration: route new requests to instances → schedule a batch (which requests, how many tokens each, and where their KV lives) → generate a trace → convert it → time it with ASTRA-Sim → account the result and retire finished requests.

Deep dive: the scheduler's decisions
# serving/core/scheduler.py — schedule_base()
# 1. chunked prefill: hand out a per-step token budget
# 2. size the KV the batch needs  -> memory.get_block_kv(...)
# 3. if it won't fit on the NPU, evict decode reqs to CPU, retry
# 4. memory.allocate(kv_size, Device.NPU)
# 5. build Batch: token lists + tier_loads=[(tier, reload_bytes, device_id), ...]

tier_loads is how "this prompt's prefix is in JBOF" becomes a real, timed memory load in the trace. serving/core/memory_model.py owns the per-tier caches and KV accounting.

Layer 2 — the intermediate trace

One human-readable text file per batch: each row is a layer of work with 11 fixed-width columns (compute time + where its input/weight/output tensors live). The loc columns (LOCAL/REMOTE/CXL/FLASH/JBOF/COLDSTORE) are what turn a plain compute layer into a timed memory access.

Deep dive: the format & the Chakra handoff
COLOCATED        model_parallel_NPU_group: 1
Layername       comp_time  input_loc  input_size  weight_loc  weight_size  output_loc ...
embedding_0     2912       REMOTE:1   144         LOCAL       1050673152   LOCAL ...
qkv_proj_2      36203      LOCAL      294912      LOCAL       50331648     LOCAL ...
jbof_load       1          LOCAL      0           JBOF:0      27493990     LOCAL ...   # a reload
serving/core/utils.py (header/formatter) ; trace_generator.py:1533–1550 (deep-tier row)

The converter llm_converter.py turns any row whose weight_loc is not LOCAL (with weight_size>0) into a MEM_LOAD node on the request's critical path. Location strings map to an enum: LOCAL=1 REMOTE=2 CXL=3 STORAGE=4 FLASH=5 JBOF=6 COLDSTORE=7.

Layer 3 — ASTRA-Sim (the timing backend)

A C++ analytical simulator. Given the per-NPU graph plus a description of the hardware, it computes the batch's time — including collective communication and memory-access contention on shared pools. config_builder.py writes it four inputs per run into astra-sim/inputs/runs/<id>/:

FileControls
workload/…/llm.N.etThe per-NPU Chakra graph (compute + memory + comm).
system/system.jsonCollective algorithms, local bandwidth.
network/network.ymlTopology, NPU counts, link bandwidth & latency.
memory/memory_expansion.jsonOur tiers — bandwidth, latency, pooling of CPU/JBOF/COLDSTORE.

It prints one line per finished batch — sys[N] iteration M finished, X cycles … — parsed back into the batch's duration (controller.py), which advances the clock. At the end, the Python layer prints the summary you read in §2d.

4. The memory tiers — what we added

A big model's KV cache does not fit in GPU memory for many long, concurrent conversations. Our extension adds a hierarchy of KV-cache tiers below the NPU; when one fills, older entries spill to the next, larger-but-slower one:

A reload's latency is the media access plus (for pooled tiers) the network hop:

reload_ns = mem_latency + bytes/mem_bw            # CPU, FLASH (local)
          + link_latency + bytes/link_bw           # + JBOF, COLDSTORE (over the BlueField/RDMA fabric)
serving/core/memory_model.py — tier_load_latency_ns()

The NPU's usable KV space is mem_size − model_weight; a heavier model both takes more NPU room and costs more KV per token — which is why our examples use a small model (see §5).

5.2  The other latencies — and why they roll up into just two knobs

A real KV reload from a deep tier crosses many latency domains — RDMA, PCIe, NVMe controllers, switch hops, flash media. The simulator does not model each hop separately; the analytical backend only needs two things per tier: a fixed per-access cost and a per-byte streaming cost. So every real-world latency term collapses into one of the config's two latency knobs: mem_latency (the tier's own media/controller access) or link_latency (the network path used to reach it). Bandwidths collapse the same way into mem_bw and link_bw.

The reload cost the simulator actually charges is:

reload_ns = link_latency + bytes/link_bw   # network path: fixed hop + streaming
          + mem_latency  + bytes/mem_bw    # tier media: fixed access + streaming

So RDMA + PCIe + switch + protocol overhead all sum into the single link_latency term (plus link_bw for the bytes), and flash-media + NVMe-controller access sum into mem_latency (plus mem_bw). GPUDirect Storage removes the host bounce-buffer entirely, so on the real machine these two terms genuinely are the whole cost. * The NPU↔NPU and CPU↔NPU paths are on-package / NVLink and are timed by ASTRA-Sim's own network model, not by a tier link_* knob — the deep-tier link_* knobs apply only to JBOF and COLDSTORE, which are reached over the Ethernet fabric.

5.3  How we simulate it faithfully

We cannot fill 288 GB of HBM or 16 TB of flash per GPU with any tractable workload. So the recipe is:

Faithfulness recipe
  1. Keep bandwidth & latency at REAL (or conservative) values — a tier's speed is physical, so mem_bw/mem_latency/link_* track the Vera Rubin figures from §5.1.
  2. Scale only the CAPACITIES, by one common factor, so the real inter-tier ratios are preserved (NPU-KV : CPU : JBOF ≈ 1 : 2.7 : 58) and a feasible workload still overflows each tier naturally.
  3. Use a small model (Llama-3.1-8B-mini4L, 4 layers) so the scaled-down NPU still keeps a healthy KV headroom over the weights.

Only mem_size is shrunk; every bandwidth and latency is the real hardware figure (or a conservative version of it). So a run on 72 of these GPUs is a Vera Rubin rack with faithful per-tier timing — only the absolute capacities and the model are scaled to fit a simulation.

5.4  Why there is no rack- or tray-local FLASH tier

Our tier chain is NPU → CPU → JBOF → COLDSTORE — the FLASH slot (a node/tray-local SSD) is deliberately left empty for the Vera Rubin configs. That matches how the real machine is built, and here is the evidence:

  1. NVIDIA's own memory taxonomy names it "G3.5", not "G3". The ladder is G1 HBM → G2 DRAM → G3 local SSD → G3.5 CMX pooled flash → G4 network storage. Solidigm states CMX "serves as Tier 3.5 memory — a level between local SSD (Tier 3), which extends capacity beyond DRAM but is not shareable across the pod, and shared storage."9 Vera Rubin's KV-offload flash is explicitly the pooled network tier (G3.5 = our JBOF), not the tray-local G3 SSD.
  2. It is physically a separate enclosure on the fabric. CMX flash lives in standalone BlueField-4 "STX" JBOF chassis (4 BlueField-4 × 150 TB = 600 TB per enclosure), connected to Rubin compute nodes over Spectrum-X Ethernet — not mounted in the compute tray.5
  3. It is reached over a network protocol, not local PCIe. Access is NVMe-oF / RDMA (with NVMe-KV extensions) across the pod fabric.4 That is a network hop by construction — the reason our JBOF tier carries link_bw/link_latency knobs and FLASH would not.
  4. Its whole purpose is pod-wide sharing. CMX exists so KV/context computed by one GPU can be reused by any GPU in the pod without recompute — which requires network reachability. A tray-local SSD, unshareable across the pod, cannot serve that role, so the design skips it.9,4
  5. The orchestration confirms the ladder. NVIDIA Dynamo's KV Block Manager tiers blocks HBM → DRAM → CMX (G3.5) → network storage (G4) via the NIXL transfer library — moving straight from CPU DRAM to the pooled context tier, with no node-local-SSD KV stage in the Vera Rubin inference path.4

So modeling a rack/tray-local FLASH tier would insert a hop the real Vera Rubin machine does not have. Keeping the slot empty — CPU DRAM spilling straight into the pooled network flash (JBOF/CMX) — is the faithful topology. (The FLASH tier remains available in the code for other hardware that does use local SSDs; it is simply unused for the Vera Rubin study.)

6. Prefix caching & eviction

Requests often share a prefix (a system prompt, a document, few-shot examples). Prefix caching reuses that prefix's KV instead of recomputing it; the tiers keep reuse possible even after the prefix is pushed out of GPU memory.

Each tier owns a RadixCache — a tree keyed by token blocks. A new request is matched against it to find the longest cached prefix, searching the shallowest tier first.

When cached, a prefix is written inclusively — into CPU and, by write-through, every deeper tier. So one prefix can live in NPU, CPU and JBOF at once; as shallow tiers fill and evict, the deeper copy survives, and a later reuse is served from the shallowest tier that still holds it.

Fidelity invariant — all spill tiers index at token granularity
Every below-NPU cache (CPU, FLASH, JBOF, COLDSTORE) is a radix tree keyed at one-token granularity (page_size = 1). This matters because a radix tree floors both what it stores and what it matches to a whole number of pages: a coarser page would silently drop any reused prefix shorter than one page. Keeping every tier token-granular guarantees the same prefix is retained and served identically no matter which tier is the storage target — so on a workload too small to overflow CPU, adding JBOF/COLDSTORE changes nothing (they stay empty and reuse is served from CPU), and TTFT is identical with or without the deep tiers. (Only the on-NPU cache pages at the KV block_size, matching how the NPU allocates KV blocks.)

The eviction rule

When a tier is full it evicts the least-recently-used entries — but only unlocked ones. An entry is locked (a lock_ref counter) while an in-flight request is using it, so it can't be evicted out from under a running batch.

The admission-safety fix
Reaching a deep tier means the NPU is constantly full and churning. The original code would try to cache a freshly-computed block into a full NPU and crash. The fix: before that allocation, if it would overflow, first evict unlocked LRU entries (they live on in deeper tiers) instead of crashing. It is a no-op when the NPU has room, verified bit-identical against an earlier study.

7. Scaling to the pod — shared JBOF & contention

A SuperPod is many racks. NPU is per-GPU, CPU/FLASH per-rack, and JBOF/COLDSTORE are one pod-wide pool shared by every rack (reached through one BlueField channel per rack). A prefix cached by any rack is reusable by every rack — and because the deep pool is shared, many racks reloading at once contend (the analytical model serializes them on the shared channel).

8. Under the hood — MEM_LOAD vs COMP-node fidelity

The contention above is only visible because of how we time a reload. There are two ways to put a reload into the trace:

  • Old — a Python "COMP node": the reload latency was a closed-form number injected as an all-LOCAL compute row. ASTRA-Sim treats it as pure compute — reloads never interfere, so a shared-pool bottleneck is invisible.
  • New — a real MEM_LOAD node: the reload is a memory load (the JBOF:dev row from §3) that ASTRA-Sim times against a shared MEMORY_POOL, so concurrent reloads serialize on the shared channel. That serialization is the contention.
1 ns anchor + formula parity
The reload row uses comp_time = 1 ns (just enough to anchor the MEM_LOAD on the critical path — no double-count), and ASTRA-Sim's memory-runtime uses the same formula as the Python model, so an uncontended reload costs exactly what it used to (regression-safe); contention is layered on top. Result: the summary's Reload(ms) is the uncontended reference; the end-to-end throughput/TTFT includes contention.
