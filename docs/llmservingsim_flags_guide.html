LLMServingSim — Flags, Config & Runnable Examples

A practical companion to the intro guide: every flag we added, the current config-file structure field-by-field, and copy-paste examples — each in two variants, with JBOF and without JBOF, on Qwen3-32B and a fast 8B twin. All numbers below are from real runs.

Running the commands
Everything runs inside the container from the repo root. Either open a shell (docker exec -it servingsim_docker bash -lc "cd /app/LLMServingSim && bash") and paste the python -m serving … lines, or wrap one command as docker exec servingsim_docker bash -lc "cd /app/LLMServingSim && python -m serving …". For the live dashboard, in a second terminal on the host: python3 serving/dashboard/serve.py → open http://localhost:8000.

0. How to use this guide

Each example gives the exact command for the WITH-JBOF config and the WITHOUT-JBOF config side by side; the two differ only by whether the config declares a jbof_mem tier. Read the scenario, copy the commands, run them, and compare the printed Tier table (hit %, reload ms) and the Latency Summary. The config files referenced below already ship in configs/cluster/; the workload files are generated by a one-line script shown with each example.

Every example ships a Qwen3-32B command (matches the config you gave — 8 GPUs / 4 CPUs, minutes per run) and a fast 8B twin (meta-llama/Llama-3.1-8B, seconds per run) so you can try it instantly and then scale up. The 8B twins are where the headline numbers below were measured.

1. The WITH / WITHOUT-JBOF trick

The whole point of a two-variant example is to isolate what the pooled JBOF tier buys you. The A/B is trivial: the same config, with the jbof_mem block present vs removed. When JBOF is absent, a prefix/context that would have parked in JBOF falls through to COLDSTORE instead — so any later reuse reloads from network storage (~2 ms/access) rather than pooled NVMe (~80 µs/access).

WITH JBOF

"num_nodes": 2,
"jbof_mem":  { "mem_size": 1.5, "mem_bw": 64, "mem_latency": 80000,
             "link_bw": 100, "link_latency": 2000 },
"coldstore_mem": { "mem_size": 4, "mem_bw": 4, "mem_latency": 2000000,
             "link_bw": 16, "link_latency": 20000 },
"nodes": [ … ]

WITHOUT JBOF (the _nojbof twin)

"num_nodes": 2,
# jbof_mem simply omitted
"coldstore_mem": { "mem_size": 4, "mem_bw": 4, "mem_latency": 2000000,
             "link_bw": 16, "link_latency": 20000 },
"nodes": [ … ]

Every *_nojbof.json in configs/cluster/ is exactly its twin minus the jbof_mem line. To make your own: python3 -c "import json;d=json.load(open('X.json'));d.pop('jbof_mem',None);json.dump(d,open('X_nojbof.json','w'),indent=2)".

Two knobs decide whether JBOF changes anything
(1) Something must actually spill — the NPU KV must fill so prefixes get evicted downward (a large NPU + a tiny workload spills nothing, so JBOF and no-JBOF look identical). (2) JBOF must be large enough to hold the reused working set — if it overflows, the reused data lands in COLDSTORE anyway and the A/B collapses. See §6.

2. The config file, field by field

Here is the config you gave, annotated. It describes 2 nodes × 1 tray = 8 GPUs and 4 CPUs: each node holds one Vera-Rubin tray = 2 superchips, and a superchip (1 CPU + 2 GPUs) is one tp_size:2 instance.

{
  "num_nodes": 2,                 # racks / nodes in the pod
  "link_bw": 1800, "link_latency": 1000,   # the COMPUTE fabric (NVLink) for TP all-reduce; GB/s, ns. -> network.yml

  # ---- POD-WIDE pooled deep tiers: declared ONCE at the top level = the pod total ----
  "jbof_mem":      { "mem_size": 30, "mem_bw": 64, "mem_latency": 80000,  "link_bw": 100, "link_latency": 2000 },
  "coldstore_mem": { "mem_size": 40, "mem_bw": 4,  "mem_latency": 2000000,"link_bw": 16,  "link_latency": 20000 },
       # mem_size  = capacity in GiB (pod total, shared by ALL nodes)
       # mem_bw    = tier read bandwidth, GB/s        mem_latency = access latency, ns
       # link_bw   = BlueField/network hop bandwidth  link_latency = hop latency, ns  (deep tiers only)

  "nodes": [
    { "num_instances": 2,          # 2 superchips in this node's tray
      "instances": [
        { "model_name": "Qwen/Qwen3-32B", "hardware": "RTXPRO6000",
          "npu_mem": { "mem_size": 33, "mem_bw": 22000, "mem_latency": 10 },  # per-GPU HBM (GiB / GB/s / ns)
          "cpu_mem": { "mem_size": 3,  "mem_bw": 1200,  "mem_latency": 120 }, # THIS superchip's host memory
          "pd_type": null, "tp_size": 2 },                              # tp_size 2 => the superchip's 2 GPUs
        { … second superchip, identical … }
      ] },
    { "num_instances": 2, "instances": [ … node 2's tray … ] }
  ]
}

2a. Topology

num_nodes × (per-node num_instances) instances, each an independent serving engine of tp_size GPUs. Here: 2 × 2 = 4 instances × TP2 = 8 GPUs; 4 superchips = 4 CPUs. The dashboard groups each node's instances into a tray (≤4 GPUs). Why TP=2, not TP=4? the profiler ships measured compute data only for tp1/tp2, and TP=2 happens to equal one superchip.

2b. The tiers

The KV hierarchy is NPU (GPU HBM) → CPU (host) → JBOF (pooled NVMe behind BlueField) → COLDSTORE (network storage). NPU is per-GPU, CPU is per-superchip (or per-node — see --cpu-scope), and JBOF/COLDSTORE are one pod-wide shared pool — a prefix cached by any GPU is reusable by every GPU. Each tier block is mem_size (GiB), mem_bw (GB/s), mem_latency (ns); the deep tiers add link_bw/link_latency for the fabric hop. The reload cost of a hit served from a tier is mem_latency + bytes/mem_bw (+ link_latency + bytes/link_bw) — this is the number that makes JBOF (fast) beat COLDSTORE (slow).

2c. Per-superchip NPU & CPU (and the de-dup)

Each instance declares its own npu_mem (per-GPU HBM) and cpu_mem (that superchip's host memory). NPU KV capacity = npu_mem − weight: Qwen3-32B weighs ~30.5 GiB/GPU (TP2), so npu_mem: 33 leaves only ~2.5 GiB for KV.

Config change: node-level cpu_mem is now optional
CPU used to be declared twice (once per node, once per instance). Now the per-superchip cpu_mem is enough — omit the node-level block and the node aggregate is derived (size = sum of the superchips'; bw/latency from the first). A node-level cpu_mem is still honored if present, and is still required only on the PIM / attention-offloading path.

3. Flags reference

FlagWhat it does
--enable-prefix-cachingTurn on the radix prefix cache (reuse a computed prefix's KV instead of recomputing). Required for any tiering.
--enable-prefix-sharingLet the shared CPU pool and the pod-wide JBOF/COLDSTORE pool serve reuse across requests/GPUs. Required for cross-GPU reuse and deep-tier spill.
--prefix-storage {CPU,FLASH,JBOF,COLDSTORE}How deep the spill chain goes. COLDSTORE = NPU→CPU→(FLASH)→JBOF→COLDSTORE (deepest). Tiers present in the config, up to this cap, are active.
--tier-policy {inclusive,exclusive}inclusive (default): a prefix is written through to CPU and every deeper tier at once. exclusive: victim cache — a prefix lives in ONE tier and is demoted one tier deeper only when the tier above evicts it (incl. NPU→CPU). §4b.
--cpu-scope {per_node,per_instance}per_node (default): one CPU pool per node, shared by its GPUs. per_instance: each superchip its own CPU; cross-GPU reuse then routes to the pod-wide JBOF/COLDSTORE. §4c.
--max-num-seqs NMax concurrent running sequences per instance (default 128). Caps in-flight KV — lower it for small-NPU configs or the live KV over-commits the NPU and aborts. §4d.
--dashboardEmit outputs/dashboard/live.json each log interval for the browser dashboard (throughput / KV-spill / TTFT / TBT over time, per-tier memory, reload bars, by-tray drill-down). §4e.
--dashboard-file PATHWhere the live JSON is written (default outputs/dashboard/live.json).
--log-interval SECHow often (sim seconds) to log a throughput sample / dashboard point (default 1.0). Lower = denser charts; must be < total sim time or the charts show "collecting samples". §4e.
--session-metricsFor multi-turn / agentic-session workloads (records with sub_requests): split TTFT into first-turn (cold) vs resumed-turn (warm, context reloaded). Exposes the pause/resume "context-parking" JBOF benefit. §4f.
--dtype / --block-size / --dataset / --outputPrecision (float16), KV block size (16), the workload JSONL, and the per-request CSV.

4. Runnable examples

Each example: generate the workload (once), then run the two variants. Watch the Tier table (which tier serves the hits, and its Reload(ms)) and the Latency Summary.

4a. Prefix caching + the storage tier (the core A/B)

A "fill then reuse" workload computes many distinct contexts (they cascade NPU→CPU→JBOF→COLDSTORE), then reuses them — so each reuse reloads from whichever tier still holds it. With JBOF the reload is fast; without it, the data sits in COLDSTORE.

guide_qwen_tiering.json is your base config with npu_mem shrunk from 33 to 30.58 (~68 MB KV) so a modest workload spills; guide_8b_tiering.json is the Llama-3.1-8B twin. Both ship in configs/cluster/ with their _nojbof variants.

Generate the workload (once)

python3 workloads/generators/make_rack_fill.py workloads/guide_fill.jsonl 16 256 8 4 3000
# 16 distinct 256-tok contexts (phase 1 fills+spills), then 16 reuses oldest-first (phase 2 reloads)

WITH JBOF

python -m serving \
  --cluster-config configs/cluster/guide_qwen_tiering.json \
  --dtype float16 --block-size 16 \
  --enable-prefix-caching --enable-prefix-sharing \
  --prefix-storage COLDSTORE --tier-policy exclusive \
  --cpu-scope per_instance --max-num-seqs 1 \
  --dataset workloads/guide_fill.jsonl \
  --output outputs/tier_jbof.csv

WITHOUT JBOF

python -m serving \
  --cluster-config configs/cluster/guide_qwen_tiering_nojbof.json \
  --dtype float16 --block-size 16 \
  --enable-prefix-caching --enable-prefix-sharing \
  --prefix-storage COLDSTORE --tier-policy exclusive \
  --cpu-scope per_instance --max-num-seqs 1 \
  --dataset workloads/guide_fill.jsonl \
  --output outputs/tier_nojbof.csv

⚡ Fast 8B twin (swap the config; runs in seconds)

# WITH:    --cluster-config configs/cluster/guide_8b_tiering.json
# WITHOUT: --cluster-config configs/cluster/guide_8b_tiering_nojbof.json   (everything else identical)
Result (measured — both the 8B twin and the Qwen3-32B tray): same 49.2% hit ratio either way, but the reuse reloads from JBOF in ~15 ms vs COLDSTORE in ~200 ms — a 13× lower reload cost purely from having the JBOF tier. (Reload cost depends on the reloaded bytes and the tier's bandwidth, not the model, so 8B and Qwen land on the same numbers here.)

4b. --tier-policy — inclusive vs exclusive

Same fill workload as 4a. inclusive eagerly copies each prefix into CPU and every deeper tier (so JBOF fills immediately, and reuse is served from the shallowest copy). exclusive is a victim cache: a prefix lives in one tier and only moves down on eviction — deeper tiers stay empty until the ones above fill. Just change one flag; run each with the WITH/WITHOUT-JBOF configs from 4a.

# inclusive (default): drop "--tier-policy exclusive"
python -m serving --cluster-config configs/cluster/guide_8b_tiering.json \
  --dtype float16 --block-size 16 --enable-prefix-caching --enable-prefix-sharing \
  --prefix-storage COLDSTORE --cpu-scope per_instance --max-num-seqs 1 \
  --dataset workloads/guide_fill.jsonl --output outputs/incl.csv
# exclusive: add "--tier-policy exclusive"  (and the _nojbof config for the no-JBOF arm)
What to look for: under inclusive the Tier table shows JBOF/COLDSTORE filling from the start (eager copies) and hits served high in the chain; under exclusive the deeper tiers stay empty until the NPU/CPU fill, then content cascades down. In both, WITH-JBOF gives a far lower Reload(ms) than WITHOUT.

4c. --cpu-scope — per_node vs per_instance

per_node: the GPUs in a node share one CPU pool, so a prefix computed on one GPU is reused from CPU by its neighbour. per_instance: each superchip has its own CPU, so cross-GPU reuse can no longer come from CPU and instead routes to the pod-wide JBOF/COLDSTORE — which is exactly where the JBOF tier earns its keep.

# per_node (default): drop the flag, or "--cpu-scope per_node"
python -m serving --cluster-config configs/cluster/guide_8b_tiering.json \
  --dtype float16 --block-size 16 --enable-prefix-caching --enable-prefix-sharing \
  --prefix-storage COLDSTORE --cpu-scope per_node --max-num-seqs 1 \
  --dataset workloads/guide_fill.jsonl --output outputs/pernode.csv
# per_instance: --cpu-scope per_instance   (+ the _nojbof config for the no-JBOF arm)
Result (example_trace, 2-GPU, measured earlier): per_node serves the whole 39-token reuse from CPU; per_instance splits it into 20 (same-GPU → CPU) + 19 (cross-GPU → JBOF). WITHOUT JBOF that cross-GPU 19 falls to COLDSTORE and its reload jumps.

4d. --max-num-seqs — concurrency & the crash it prevents

Small-NPU configs (like the ones here, ~2.5 GiB KV) can only hold a few requests' live KV at once. The default (128) lets the scheduler admit too many; their locked in-flight KV over-commits the NPU and the run aborts with NPU: tried to load X but only Y is available. The fix is to cap concurrency so the live set fits — which also lets finished prefixes accumulate and spill.

# crashes: --max-num-seqs 128 (default) on a small-NPU config + a heavy workload
# works:   --max-num-seqs 1   (used throughout this guide for the tight-NPU examples)
Rule of thumb
Keep max_num_seqs × (largest request's KV) < NPU KV capacity. For these tight configs that means --max-num-seqs 1; for roomy NPUs, 8 is a good default. JBOF/no-JBOF does not change this.

Add --dashboard to any run to stream metrics to the browser; --log-interval sets the sampling cadence. Use the fill workload from 4a so the tiers actually move.

4f. --session-metrics — the decode use-case (context parking)

A conversation's KV is parked to a lower tier while the user is idle between turns, then reloaded to answer the next turn. With JBOF that reload is fast; without it, the conversation state falls to COLDSTORE. --session-metrics splits TTFT into first-turn (cold) vs resumed-turn (warm) so the reload tier shows up directly.

The session workload format — what's new vs a flat trace

Every workload so far has been flat: one JSONL line = one independent request, with all arrival times fixed up front. A session workload is different: one JSONL line = one whole conversation, and its turns form a dependency chain released over time.

Flat request (all earlier workloads)

{ "input_toks": 128,
  "output_toks": 64,
  "arrival_time_ns": 0,
  "input_tok_ids":  [ … prompt token ids … ],
  "output_tok_ids": [ … generated ids … ] }
# one line = one request, arrives at arrival_time_ns

Session record (multi-turn)

{ "session_id": "s0",
  "arrival_time_ns": 0,
  "sub_requests": [
    { "input_toks": 528, "output_toks": 16,
      "input_tok_ids":  [ … ], "output_tok_ids": [ … ],
      "tool_duration_ns": 500000000 },   # turn 0, then idle 500 ms
    { "input_toks": 560, "output_toks": 16,
      "input_tok_ids":  [ … ], "output_tok_ids": [ … ],
      "tool_duration_ns": 500000000 },   # turn 1
    { … turn 2 … } ] }
# one line = one SESSION; sub_requests = the turns

So a session record carries three things a flat record does not:

Extra fieldMeaning
session_idGroups the turns into one conversation. It rides through to each request so --session-metrics and the dashboard can split first-turn (cold) from resumed-turn (warm). (Informational — it does not change scheduling.)
sub_requests[]The list of turns. Each turn has the same fields as a flat request (input_toks, output_toks, input_tok_ids, output_tok_ids) plus tool_duration_ns.
tool_duration_nsThe idle gap after this turn before the next turn is released — the "user is thinking" / tool-call window during which the conversation is parked (its KV can be evicted downward). This is the knob that creates the pause/resume behavior.
Two behaviors a flat trace can't express
(1) Dynamic release. Only turn 0 is queued at arrival_time_ns; each later turn is released by the router at (previous turn's completion + tool_duration_ns) — the turns are a dependency chain, not fixed arrivals. (2) A growing shared prefix. By convention (and as make_multiturn.py builds it), turn t's input_tok_ids = turn t−1's (input_tok_ids + output_tok_ids) + a few new user tokens. So the accumulated conversation is one long shared prefix that a later turn reloads from cache/tier instead of recomputing — and if it was evicted to JBOF/COLDSTORE while idle, that reload is the JBOF-vs-COLDSTORE cost this example measures. (The loader also accepts these session records via the same --dataset flag; it auto-detects sub_requests.)

5. Realistic sharegpt showcase

For production-like traffic, use a real trace instead of a generated one. The only change from §4a is the dataset (and bounding concurrency so the tight NPU isn't over-committed):

python -m serving --cluster-config configs/cluster/guide_qwen_tiering.json \
  --dtype float16 --block-size 16 --enable-prefix-caching --enable-prefix-sharing \
  --prefix-storage COLDSTORE --tier-policy exclusive --cpu-scope per_instance \
  --max-num-seqs 8 --dashboard --log-interval 1 \
  --dataset workloads/sharegpt-qwen3-32b-300-sps10.jsonl --output outputs/sharegpt_jbof.csv
# WITHOUT JBOF: swap to guide_qwen_tiering_nojbof.json
Expect minutes, not seconds
300 requests on 8 Qwen3-32B GPUs is a real run. Watch the dashboard; compare the Tier table's total reload and the Latency Summary between the two configs. If nothing spills, shrink npu_mem toward the weight (~30.6) so the KV cache is small; if JBOF fills to ~100% with hits landing in COLDSTORE, grow jbof_mem (see §6).

6. Sizing rules (so runs don't crash and JBOF actually matters)

SymptomCauseFix
Crash: NPU: tried to load X but only Y availableToo many concurrent requests' locked KV for the NPU KV capacity (npu_mem − weight).Lower --max-num-seqs (1 for tight NPUs), or raise npu_mem so KV ≥ one grown request.
CPU/JBOF/COLDSTORE all 0%, hits 0NPU never fills — nothing spills (large NPU + small workload).Shrink npu_mem toward the weight, or use a bigger/fill workload.
WITH-JBOF looks identical to WITHOUTJBOF overflows → reused data lands in COLDSTORE either way.Grow jbof_mem ≥ the reused working set (≈ #distinct contexts × context KV; a context costs 2× the bytes in CPU/JBOF/COLDSTORE that it does in the NPU, since the pooled tiers count both TP ranks).
A tier never fills even under pressureUnder exclusive, an evicted prefix that can't fit the tier below is dropped (KV is recomputable).Give each tier ≥ one prefix's worth of capacity.
Dashboard charts say "collecting samples"--log-interval ≥ total sim time → <2 points.Lower --log-interval, or run a longer workload.
The one-line mental model
JBOF only changes a number when (a) the NPU spills, (b) the spilled data is later reused, and (c) JBOF is big enough to be the tier that serves that reuse. Then JBOF's ~80 µs/access beats COLDSTORE's ~2 ms/access, and you see it in Reload(ms), TTFT, and throughput.
