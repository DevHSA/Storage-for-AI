⚡ Average throughput (tok/s)
How this is calculated
Technical Cumulative-average total token rate at each sim-time t: mean_tps(t) = (Σ (prompt_tps + decode_tps) · Δ up to t) / t — total tokens produced so far ÷ elapsed sim time. Converges to the whole-run average (the average throughput headline tile).
In plain words The running average tokens-per-second (prompt + output) since the run began — not the instantaneous rate, but the average so far. It settles toward the final overall throughput as the run proceeds.
⏱️ Average TTFT (ms)
How this is calculated
Technical ttft = mean( r.ttft for r in every scheduler's done list ), where r.ttft = first_token_time − arrival. The cumulative mean over finished requests, sampled each Δ; value in ms. (Same metric as the "Average TTFT" headline tile.)
In plain words The average time from a request arriving to its first output token, averaged over all requests finished so far. It reads 0 until the first request completes, then settles to the true average.
⏱️ Average request completion time (ms)
How this is calculated
Technical e2e = mean( r.latency for r in done ), where per request latency = end_time − arrival (full request turnaround). The cumulative mean over finished requests, sampled each Δ; value in ms. (Same metric as the "Average request completion time" headline tile.)
In plain words The average total time from a request arriving to its last output token — the whole answer's turnaround — averaged over all requests finished so far.
🧠 KV spill memory
How this is calculated
Technical Per tier, sampled each Δ: used_bytes = (tokens held in that tier's pool) × (KV bytes per token), stacked CPU → FLASH → OCTEON JBoF → COLDSTORE. NPU HBM is excluded here (shown in its own panel). KV bytes/token = 2 × kv_heads × head_dim × layers × dtype_bytes ÷ tp_size (pooled tiers store the full context, so ×tp_size).
In plain words How much KV cache has overflowed out of GPU memory into each slower tier. It only grows once the GPU fills up; if the GPU never fills, these stay at zero.

🔻 Request statistics

How this is calculated
Technical Cumulative funnel over all requests. The denominator is the total request count parsed from the workload file up front (est_total_requests: one per line for flat schema, one per sub_request for sessions; falls back to the live routed count). Persistent per-request flags: arrived = arrival ≤ clock; started = queuing_delay ≥ 0 (first prefill chunk admitted, scheduler.set_que_delay); decoding = ttft ≥ 0 (first output token produced). They nest: arrived ≥ started ≥ decoding.
In plain words The stages of a request's life: it arrives, then starts being served (prefill begins), then enters decode (first word out). Each bar is how many requests have reached that stage so far — the gaps are requests currently stuck at each stage (queued or prefilling). The total is known ahead of time by reading the workload file, so the bars fill toward the true final count.

🧠 Memory by tier

🧠 Memory by tier (now)

How this is calculated
Technical A snapshot at the current sim-time. Per tier: used = (tokens in pool) × (KV bytes/token), cap = configured mem_size, %used = used / cap. NPU is per-GPU; CPU is per-node or per-instance (see --cpu-scope); OCTEON JBoF/COLDSTORE are one pod-wide shared pool.
In plain words How full each memory tier is right now — GPU HBM at the top, then progressively slower/larger tiers it spills into.

🎯 Prefix cache

How this is calculated
Technical hit_ratio = Σ hit_tokens / Σ requested_prompt_tokens. Per tier: hit_tokens = prompt tokens served from cached KV in that tier; reload_ms = Σ ( mem_latency + bytes/mem_bw [+ link_latency + bytes/link_bw] ) over reloads pulled up from that tier into the GPU.
In plain words How much prompt work was skipped by reusing previously-computed KV (higher hit % = less recompute), and how long it cost to pull that reused data back up from each tier. Fast tiers (OCTEON JBoF) add little; slow ones (COLDSTORE) add a lot.

⏱️ Latency (ms)

How this is calculated
Technical Percentiles (mean/p50/p90/p99/max) over all finished requests, per metric: TTFT = first_token − arrival; TBT/token = (end − first_token)/(output−1); ITL = individual inter-token gaps (every step, so its distribution is widest); E2E = end − arrival.
In plain words The spread of the key latencies across finished requests — typical (mean/p50) and worst-case tail (p90/p99/max). TTFT = wait for first word; TBT/ITL = pace of words after that; E2E = total time from ask to fully-answered.

🖥️ Compute drill-down

A tray = up to 4 GPUs (2 superchips); CPUs = distinct host-memory pools it owns.
How this is calculated
Technical Per GPU (or aggregated per tray): current running vs waiting request counts, NPU-HBM used/cap, and tokens processed — summed from each instance's scheduler and memory model at the current snapshot.
In plain words A per-GPU (or per-tray) breakdown of how busy each unit is and how much of its memory is in use right now — handy for spotting imbalance.

💬 Session / resume latency (multi-turn "context parking")

A resumed turn reloads the conversation's parked context from a lower tier before answering — that reload lands in its TTFT. With OCTEON JBoF the reload is fast; without it the context falls to COLDSTORE and resumed-turn TTFT climbs. Cold first-turn has no reload.
How this is calculated
Technical Finished requests are split by sub_request_index: 0 = first turn (cold), ≥1 = resumed turn (warm). TTFT percentiles are computed for each group; resume_overhead = resumed.mean − first.mean.
In plain words Only shown for multi-turn/agent workloads. It compares the first-token wait on a brand-new conversation vs a paused one being resumed — the gap is the cost of reloading the parked conversation from a lower memory tier.

🖥️ NPU HBM (weight + KV, per instance)

How this is calculated
Technical Per GPU (per TP rank): used = weight_bytes/tp + KV-shard bytes, cap = npu_mem, %used = used/cap. weight_bytes ≈ params × dtype_bytes; KV/token = 2 × kv_heads × head_dim × layers × dtype_bytes ÷ tp; KV/block = KV/token × block_size. A TP=N instance spans N GPUs, each holding weight/N + its KV shard.
In plain words How much of each GPU's memory is taken by the model weights plus its share of the KV cache. If "%used" never gets high, nothing spills to the slower tiers — which is why the KV-spill and prefix-reload panels can stay empty.
