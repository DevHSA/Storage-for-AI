⚡ Throughput over sim time

How this is calculated
Technical Two lines sampled once per --log-interval Δ (here 1 s). prompt_tps = (prompt/prefill tokens processed during Δ) / Δ; decode_tps = (output/decode tokens processed during Δ) / Δ. Internally tokens accrued in the interval are scaled by FREQ/INTERVAL (INTERVAL = log_interval×FREQ, FREQ = 1e9 ns/s).
In plain words How many prompt tokens (reading the question) and output tokens (writing the answer) the whole cluster produces each second, plotted over time. Prompt work dominates while requests arrive; when arrivals stop, decode takes over and its line jumps up.

🧠 KV spill memory over sim time

Stacked usage of the spill tiers (CPU → deep tiers). NPU HBM shown separately below.
How this is calculated
Technical Per tier, sampled each Δ: used_bytes = (tokens held in that tier's pool) × (KV bytes per token), stacked in order CPU → FLASH → JBOF → COLDSTORE. NPU HBM is excluded here (shown in its own panel). KV bytes/token = 2 × kv_heads × head_dim × layers × dtype_bytes ÷ tp_size (pooled tiers store the full context, so ×tp_size).
In plain words How much KV cache has overflowed out of GPU memory into each slower tier as the run goes. It only grows once the GPU fills up; if the GPU never fills, these stay at zero.

⏱️ TTFT over sim time (by completion)

How this is calculated
Technical ttft = mean( r.ttft for r in every scheduler's done list ), where r.ttft = first_token_time − arrival. Aggregated over finished requests only (a request enters done after its last token), so a request contributes to this line only once it has fully completed. Value in ms.
In plain words Average time-to-first-token — but counting only requests that have completely finished. Because a request isn't counted until it's done generating all its tokens, this line stays at 0 until the first request finishes, then jumps. It's the true value, just reported late.

⏱️ TBT over sim time

How this is calculated
Technical tbt = mean( r.tpot for r in done ), where per request tpot = (end_time − first_token_time) / (output_tokens − 1) (time-per-output-token). Aggregated over finished requests; value in ms.
In plain words Average gap between two consecutive output tokens, for finished requests. It rises when each GPU is decoding many sequences at once and as each sequence's context grows longer.

⏱️ TTFT at first-token time NEW

How this is calculated
Technical For each interval (t_prev, t_now], average the TTFT of requests whose first token landed in that interval: ttft_ft = mean( r.ttft for r where t_prev < (r.arrival + r.ttft)/FREQ ≤ t_now ), scanning requests that have started decoding (in a running batch) or finished (in done). Binned by first-token time, not completion time. Empty intervals (no new first tokens) read 0.
In plain words The real time-to-first-token as it actually happens, plotted at the moment each request emits its first token — so you see the true (low, flat ~200 ms) TTFT throughout the run instead of the 0-then-jump of the "by completion" chart on the left. It drops to 0 after arrivals stop, because no new first tokens are being produced then.

🔎 Why two TTFT charts?

Both use the same per-request TTFT (first_token − arrival); they differ only in when each request is plotted on the time axis:
  • By completion (left) plots a request once it has fully finished. With long generations this lags a lot — the line is 0 until the first request completes, then jumps to the true value.
  • At first-token time (new) plots a request the instant it produces its first token. This shows the true, low, flat TTFT live — no lag.
If the two disagree in shape but agree in final value, that's expected: same numbers, different x-axis placement.

🧠 Memory by tier (now)

How this is calculated
Technical A snapshot at the current sim-time. Per tier: used = (tokens in pool) × (KV bytes/token), cap = configured mem_size, %used = used / cap. NPU is per-GPU; CPU is per-node or per-instance (see --cpu-scope); JBOF/COLDSTORE are one pod-wide shared pool.
In plain words How full each memory tier is right now — GPU HBM at the top, then progressively slower/larger tiers it spills into.

🎯 Prefix cache

How this is calculated
Technical hit_ratio = Σ hit_tokens / Σ requested_prompt_tokens. Per tier: hit_tokens = prompt tokens served from cached KV in that tier; reload_ms = Σ ( mem_latency + bytes/mem_bw [+ link_latency + bytes/link_bw] ) over reloads pulled up from that tier into the GPU.
In plain words How much prompt work was skipped by reusing previously-computed KV (higher hit % = less recompute), and how long it cost to pull that reused data back up from each tier. Fast tiers (JBOF) add little; slow ones (COLDSTORE) add a lot.

⏱️ Latency (ms)

How this is calculated
Technical Percentiles (mean/p50/p90/p99/max) over all finished requests, per metric: TTFT = first_token − arrival; TBT/token = (end − first_token)/(output−1); ITL = individual inter-token gaps (every step, so its distribution is widest); E2E = end − arrival.
In plain words The spread of the key latencies across finished requests — typical (mean/p50) and worst-case tail (p90/p99/max). TTFT = wait for first word; TBT/ITL = pace of words after that; E2E = total time from ask to fully-answered.

🖥️ Compute drill-down

A tray = up to 4 GPUs (2 superchips); CPUs = distinct host-memory pools it owns.
How this is calculated
Technical Per GPU (or aggregated per tray): current running vs waiting request counts, NPU-HBM used/cap, and tokens processed — summed from each instance's scheduler and memory model at the current snapshot.
In plain words A per-GPU (or per-tray) breakdown of how busy each unit is and how much of its memory is in use right now — handy for spotting imbalance.

💬 Session / resume latency (multi-turn "context parking")

A resumed turn reloads the conversation's parked context from a lower tier before answering — that reload lands in its TTFT. With JBOF the reload is fast; without it the context falls to COLDSTORE and resumed-turn TTFT climbs. Cold first-turn has no reload.
How this is calculated
Technical Finished requests are split by sub_request_index: 0 = first turn (cold), ≥1 = resumed turn (warm). TTFT percentiles are computed for each group; resume_overhead = resumed.mean − first.mean.
In plain words Only shown for multi-turn/agent workloads. It compares the first-token wait on a brand-new conversation vs a paused one being resumed — the gap is the cost of reloading the parked conversation from a lower memory tier.

🖥️ NPU HBM (weight + KV, per instance)

How this is calculated
Technical Per GPU (per TP rank): used = weight_bytes/tp + KV-shard bytes, cap = npu_mem, %used = used/cap. weight_bytes ≈ params × dtype_bytes; KV/token = 2 × kv_heads × head_dim × layers × dtype_bytes ÷ tp; KV/block = KV/token × block_size. A TP=N instance spans N GPUs, each holding weight/N + its KV shard.
In plain words How much of each GPU's memory is taken by the model weights plus its share of the KV cache. If "%used" never gets high, nothing spills to the slower tiers — which is why the KV-spill and prefix-reload panels can stay empty.
